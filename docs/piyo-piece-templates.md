# ぴよ将棋 駒テンプレ画像の命名規則

**入手経路**: ぴよ将棋アプリ内部データ (JB 端末経由取得)
**配置**: `assets/piyo/k{デザインID}/k{デザインID}_{駒コード}_Normal.png`

420 枚のテンプレ画像は 14 デザイン × 30 駒 で構成される。これを **pHash 辞書** に変換して駒認識に使う。

## パス構造

```
assets/piyo/
├── k1/     ぴよ将棋標準 (オレンジ枠、丸い書体)
├── k2/     木目・楷書 (「王将」フル表記)
├── k3/     木目・楷書 (「王」略字)
├── k4/     木目・角ばった書体
├── k5/     木目・細身楷書
├── k6/     木目・省略書体
├── k7/     木目・草書系
├── k101/   ダーク: 黒背景・白文字
├── k102/   ダーク: 暗茶木目・楷書
├── k103/   ダーク: 暗茶木目・略字
├── k104/   ダーク: 手書きポップ書体
├── k105/   ダーク: 暗茶木目・楷書 (「王将」)
├── k106/   ダーク: 濃茶木目・略字
└── k107/   ダーク: 濃茶木目・楷書
```

**規則**: `k1〜k7` = ライトモード、`k101〜k107` = ダークモード、番号の末尾が対応関係を暗示 (k2 ↔ k102 は同じ書体テーマ)。

## ファイル名フォーマット

```
k{デザインID}_{向き}{バリエ}{駒種}_Normal.png
                └─┬─┘└─┬─┘└─┬─┘
                  │    │    └── 駒種 (0-7)
                  │    └────── バリエ (0=生駒/王, 1=成駒/玉)
                  └──────────── 向き (0=先手, 1=後手180度回転)
```

### 駒種コード (3桁目)

| 番号 | 駒 |
|---|---|
| 0 | 王/玉 |
| 1 | 飛車 |
| 2 | 角行 |
| 3 | 金将 |
| 4 | 銀将 |
| 5 | 桂馬 |
| 6 | 香車 |
| 7 | 歩兵 |

### バリエコード (2桁目) — 3桁目と組み合わせる

| コード | 意味 |
|---|---|
| `000` | 王将 |
| `001` | 飛車 |
| `002` | 角行 |
| `003` | 金将 |
| `004` | 銀将 |
| `005` | 桂馬 |
| `006` | 香車 |
| `007` | 歩兵 |
| `010` | 玉将 (王の対、後手側で使われる字体) |
| `011` | 龍王 (飛車成) |
| `012` | 龍馬 (角行成) |
| **`013`** | **欠番** (金は成らないため) |
| `014` | 成銀 (全) |
| `015` | 成桂 (圭) |
| `016` | 成香 (杏) |
| `017` | と金 (歩成) |

**注意**: `010` は「成王」ではなく **「玉将」**。将棋の慣習で先手が王将、後手が玉将を使うため、ぴよ将棋も別画像として持っている。

### 向きコード (1桁目)

- `0xx` = 先手向き (正立)
- `1xx` = 後手向き (180度回転済み)

例:
- `k1_000_Normal.png` = 先手・王将
- `k1_010_Normal.png` = 先手・玉将
- `k1_100_Normal.png` = 後手・王将 (回転済み)
- `k1_017_Normal.png` = 先手・と金
- `k1_117_Normal.png` = 後手・と金 (回転済み)

## ファイル数の検算

1 デザイン当たり:
- 生駒 8 種 (王/玉/飛/角/金/銀/桂/香/歩) × 先手/後手
  - 王・玉は別画像なので 2 種扱い → 生駒 8 種 × 2 向き = 16 枚
  - ただし 000-007 と 010 のみで **9 枚 × 2 向き = 18 枚だけど、玉は先後どちら側でも出るので** 実装上は 010 も両向きで持つ (2 枚)
- 成駒 5 種 (龍/馬/成銀/成桂/成香/と) × 先手/後手 → 6 種 × 2 向き = 12 枚

**合計 = 30 枚 / デザイン** ✅ (実測と一致)

**総計 = 14 デザイン × 30 枚 = 420 枚**

## SFEN テンプレキーへのマッピング

pHash 辞書のキーは `{向き}_{promo}{駒種}` 形式 (既存 `templateKey` 関数と一致):

| ファイル 3桁コード | SFEN キー例 (先手) | SFEN キー例 (後手) |
|---|---|---|
| 000 | `B_K` (王) | `W_K` (玉、後手側で王画像を使う場合) |
| 010 | `B_K` (玉。先手先玉派) | `W_K` (玉、標準用途) |
| 001 | `B_R` | `W_R` |
| 002 | `B_B` | `W_B` |
| 003 | `B_G` | `W_G` |
| 004 | `B_S` | `W_S` |
| 005 | `B_N` | `W_N` |
| 006 | `B_L` | `W_L` |
| 007 | `B_P` | `W_P` |
| 011 | `B_+R` (龍) | `W_+R` |
| 012 | `B_+B` (馬) | `W_+B` |
| 014 | `B_+S` (成銀) | `W_+S` |
| 015 | `B_+N` (成桂) | `W_+N` |
| 016 | `B_+L` (成香) | `W_+L` |
| 017 | `B_+P` (と金) | `W_+P` |

**注意**: 王 (000) と玉 (010) は SFEN 上ではどちらも `K` に潰される。**認識時は 000 と 010 のどちらが hit しても正解**。辞書に両方入れておいて距離が近い方を採用する運用。

## デザイン ID と `AppProfile.designId`

将来アプリ判別ロジックを実装するとき (#3 は削除済みだが、複数デザインの選別は必要)、盤面の左上マスあたりの平均色や輝度から **どのデザインが使われているか** を推定して、対応する `k*` 辞書を選ぶ。

暫定戦略: **全 14 デザインの辞書を全部持っておいて、各マスの最近傍を全辞書横断で探す**。420 テンプレ × 81 マス = 34,020 回の Hamming 距離計算だが、64bit ビット演算なので数 ms で終わる。

## 生成される辞書ファイル

```
data/ocr/templates/piyo.json           # 14 デザイン全部を含む単一辞書
data/ocr/templates/piyo-light.json     # k1-k7 のみ
data/ocr/templates/piyo-dark.json      # k101-k107 のみ
```

デザイン ID をキーの一部として区別する (例: `k1:B_P`, `k101:B_P`)。

## 生成コマンド

```bash
bun run ocr:template piyo assets/piyo
# → data/ocr/templates/piyo.json (全 420 テンプレ)
```

既存の `generate-template.ts` はフラットなフォルダを想定していたので、この命名規則パーサを追加する (#24)。
