# 学習/推論解像度のトレードオフ (w224 vs w384)

BoardOCR を **どの入力解像度 (`IMAGE_SIZE`) で学習・推論するか** の判断材料をまとめる。実測データは w224 sweep ([`ocr-scaling-outlook.md`](./ocr-scaling-outlook.md), 2026-07-12) と w384 sweep ([`w384-sweep-analysis.md`](./w384-sweep-analysis.md), 2026-07-13) の 2 世代。backbone 選定は [`backbones.md`](./backbones.md) に、指標定義は [`ocr-metrics.md`](./ocr-metrics.md) にある。

## 前提: 「画質」の中身を分けて考える

「入力画像の解像度」には 2 つの独立した軸があって、これを混ぜると議論が噛み合わなくなる:

1. **元キャプチャの解像度** — スマホの実サイズ (iPhone 15 なら 1290x2796px、盤クロップ後で 900〜1200px 四方)
2. **モデル入力にリサイズする解像度** — `IMAGE_SIZE` (train も infer も同じサイズで揃えるのが基本)

`ultemica/piyoshogi` の実キャプチャは元画像がだいたい 800〜1200px 四方あるので、**元画質としては w224 でも w384 でも「縮小して入れている」状態**。「w224 ばかりの実運用画像だから w384 学習は無駄」というのは実は当たっていない — うちのケースだと元画像は常に 384 より大きく、w384 で入れた方が情報量が保存される側。

「入力が本当に低画質になる」パターンは:

- SNS 経由 (Twitter リサイズで 480px 四方に潰される)
- スクショの縮小配信
- 古い端末の画面キャプチャ

このときは w384 に blow up しても新しい情報は湧かないので、w384 学習の恩恵は消える。

## 学習解像度ごとのメリット・デメリット

### w224

**メリット**

- **学習が速い**: VRAM も wall-clock も概ね `(384/224)^2 ≈ 2.9倍` 軽い。9 backbone × 50ep が現実的な時間で回る。
- **推論も 2.9 倍速い**: edge / ブラウザ配信で明確な差。特に WASM や mobile CPU では体感が変わる。
- **augmentation の効きが強く出る**: 情報が減っている分、augmentation で「見えづらいけど当てる」学習が乗る。SNS 経由の粗い画像には w224 学習の方がロバストになりやすい (要 realistic 実測)。

**デメリット**

- **1 マスあたり ~24.9px**、成香 / 成桂 / 成銀の点画が潰れる領域に片足入る。cell_acc 0.966〜0.994 で頭打ち (w224 sweep 実測)。
- **sfen exact-match の上限が 0.72 程度** (w224 sweep の convnext_tiny)。90% ラインには蒸留 + 後処理を積まないと届かない。
- 元画像が高解像度でも情報を捨てている。**手持ちのデータの上澄みを使い切れない**。

### w384

**メリット**

- **1 マスあたり ~42.7px**、細部が完全に見える。cell_acc が全 backbone 1.000 に張り付く (w384 sweep 実測)。
- **sfen exact-match 0.995〜0.999** に到達。convnext_tiny なら 20ep で 0.995、つまり「早く」「高く」到達する。
- 元画像が w384 以上ある実キャプチャに対しては情報損失ゼロ。
- **backbone を小さく選べる**: mobilenet_v3_large (3.3M) で val sfen 0.995 まで出る。w224 では convnext_tiny (28M) が必要だったのが、解像度で稼いだ分 params を落とせる。**モデル容量と解像度は代替可能** で、w384 は「モデルを軽くできる予算」を稼いでくれる。

**デメリット**

- **学習コストが 2.9 倍** (w384 sweep 実測: 5 backbone × 200ep で GPU 5 枚並走 3h35m)。
- **推論コストも 2.9 倍**: WASM / edge で厳しい。ブラウザ配信を狙うなら w384 の推論時間で成立するか実測が必要。
- **元画像が低解像度の入力に対して伸び代がない**: 320x320 の入力を 384 に blow up しても cell 内は依然として細部が潰れたまま。**w224 で学習したモデルの方が「粗い画像に慣れている」ので有利** な可能性すらある。
- augmentation で作ったノイズがそのまま「解像度に余裕がある版のノイズ」になり、実運用の SNS 経由粗画像への転移が w224 より弱くなるリスク (要 realistic 実測)。

## 実測値サマリ (val sfen_full, 同 backbone 比較)

| Backbone | w224 × ep50 | w384 × ep50 | w384 × ep200 (最終) |
|---|---:|---:|---:|
| mobilenet_v3_small | 0.385 | 0.904 | 0.976 |
| mobilenet_v3_large | 0.593 | 0.976 | 0.995 |
| efficientnet_b1    | 0.663 | 0.994 | 0.999 |
| convnext_nano      | 0.660 | 0.991 | 0.999 |
| convnext_tiny      | 0.716 | 0.997 | 0.999 |

- w224 → w384 で **全 backbone が +25〜60pt 跳ねる**。cell_acc の 1pt 改善が 81 マス掛け算で sfen に効くため。
- w384 × ep50 の時点で **既に w224 × ep50 の 2 世代上の backbone より上**。「解像度は backbone 昇格 2 段分」の効き。
- ただし **val 分布に穴がある** (count≥11 が 0 件、飛の非ゼロ率が train の約半分) ため、w384 側の 0.99+ 帯は上限に張り付いた数字。realistic での差はもっと縮む可能性がある。

## 運用シナリオ別の判断

| 想定入力 | 推奨学習解像度 | 理由 |
|---|---|---|
| 手持ちスマホの直キャプチャ (800px+) | **w384** | 元画像の情報が生かせる。cell 詳細が読める。 |
| SNS 経由 (Twitter リサイズ ~500px) | w224 と w384 の両方で realistic 評価。おそらく **w224 のほうがロバスト** | 入力の実質解像度が w384 側で活きない、augmentation の噛み合いも w224 側の方が良い可能性大 |
| ブラウザ WASM 配信 (推論速度クリティカル) | **w224 + 小 backbone** or **w384 + mobilenet_v3_large** | 推論 FPS の実測次第。w384 で backbone を小さくして帳尻を合わせるのは有効 |
| edge / mobile 常時起動 | **w224** | 推論速度と電力の両方で有利 |
| クラウド API (精度優先) | **w384** | コストは吸収できる。0.999 帯が使える |

## 「w224 ばかりで判定する運用なのに w384 で学習しても無駄」は半分正しい

**正しい部分**:

- **w224 ネイティブの入力に対しては、w384 学習モデルの「解像度で稼いだ精度」は実現しない**。cell 内の細部が入力側に無いので、モデルが見たいものが物理的に見えない。

**不正解な部分**:

- **元画像が w384 以上あるなら、たとえ最終的に w224 で inference しようが、学習は w384 でやった方が良い**、というわけではない。**学習と推論の解像度は揃えるのが基本**。学習 w384 / 推論 w224 のような gap を作ると、モデルは w384 前提で作った特徴 (細部依存) を捨てる必要が出る。
- なので実運用が w224 なら学習も w224、実運用が w384 相当なら学習も w384。

## 実務的な提案 (2026-07-13 時点)

1. **realistic 評価を w224 と w384 両方でやる** ([`../TRAINING_PLAN.md`](../TRAINING_PLAN.md) §1 の realistic 再測定の中で)。これをやらないと「w384 で val 0.999 が出た」ことがどれだけ実運用に転移するか分からない。
2. w384 sweep で **mobilenet_v3_large (3.3M) が val 0.995** まで出せたのは大きな発見。もし w224 で同精度を狙うと convnext_tiny (28M) が必要だった。**解像度と backbone のトレードで、w384 + 中サイズが Pareto 最良になった可能性が高い**。
3. **配信形態が決まってから最終学習をやる** のが理想。edge / WASM なら w224 + mnv3l 再学習、クラウドなら w384 + effb1、両方欲しいならそれぞれ別モデルを持つ (backbone 選定は既に候補が絞れた)。

要するに **w384 は「元画像に余裕があるとき」の解像度で、SNS 粗画像を主眼にするなら w224 側も残しておく価値がある**。realistic 評価で両者の落差を測るのが次の意思決定材料。
